# Boat Manager 1.5.1 — release plan

Drafted 19 September 2026, against `main` of the app repo at `46008ca` ("1.5.0")
and `e6d4c25` of this repo.

## The rule for this release

1.5.1 is a point release behind a shipped 1.5.0. It fixes what 1.5.0 broke or left
unfinished, and adds only what is small enough to be verified in a week. No new
entities, no store migration beyond additive optional attributes, no feature that
needs a season of data to prove itself. Everything else is 1.6.

Two lists were merged to build this: the BoatManager Todoist project (28 open
items) and the unfinished build-order steps in `claude/vsc-feature-spec.md` and
`claude/expenses-feature-spec.md`.

## Tier 1 — Defects. 1.5.1 does not ship without these.

### 1. Upkeep dashboard misses maintenance log entries — M

Todoist: *Check Hull zincs code — upkeep dashboard not finding the log entries*;
*Link equipID rather than link by name*. These are one bug, not two.

The dashboard matches a logged task to a piece of equipment by **string equality
on names**:

- `Boat Manager 2/Shared/UpkeepStatus.swift:259` — `trackerNames.contains(normalized(task.taskName))`
- `UpkeepStatus.swift:261` — the task's equipment list must *contain* the row's equipment name
- `UpkeepStatus.swift:273` — `maintenanceEquip` is a **comma-separated string of equipment names**, split and lowercased
- `Boat Manager 2/Shared/CoreData/CDFunctions.swift:353-372` — `autoLinkMaintenanceItems` links by `equipType` string equality too

Consequences, all silent: rename a piece of equipment and its history detaches;
"Hull Zincs" never matches an item named "Zincs — Hull"; a comma inside an
equipment name splits it into two phantom entries.

**The fix must not write to anything the user did not edit.** The app's design rule
is that the day log stands alone and changes only when the owner explicitly changes
it — a near-legal record — with equipment maintenance as the deliberate relational
exception, because nothing else worked. A launch-time migration that silently
re-links historical records is exactly what that rule forbids, whatever it fixes.
So:

1. **Read-time resolution, no writes.** The dashboard resolves by `equipID` where
   one exists and falls back to the existing name match where it does not. The
   fallback stays permanently; it is not a migration step. An owner who never acts
   on anything sees the app behave exactly as it does today.
2. **Write `equipID` only on an explicit save.** A maintenance task records the
   link when the owner creates or edits it. Data changes when the owner changes it,
   and never otherwise.
3. **Legacy rows become a Data Health finding**, not a background repair — "this
   task names equipment that matches nothing", with the proposed link and a Fix
   button. 1.5.0 already established the pattern and the wording: nothing changes
   until you tap Fix.
4. **Nothing touches `Log`.** `equipID` lives on `MaintenanceTasks`, which is the
   relational exception the design already sanctions.

**What a historical log prints does not change.** `ListLogPDFView:184-188` prints
`log.maintenanceTask` — the stored summary string — and only falls back to a live
count of the relationship when that string is empty. The log carries its own text
snapshot, so re-linking a task cannot rewrite what an old log says. Worth
confirming in test, because it is the property that makes this safe.

**One thing to know before deciding.** Two launch passes already write to `Log`
with no user action, both shipped:

- `CDFunctions.swift:298-311` — `backfillMaintenanceTaskSummaries` writes
  `log.maintenanceTask`, a field that is displayed, filtered on and printed.
- `CDFunctions.swift:321-334` — `repairNegativeLogHours` writes `hrsUnderway`,
  `hrsEngine`, `hrsGenSet` on logs that went negative.

Both are defensible repairs, and `repairNegativeLogHours` is idempotent and
documented as safe. But the stated rule is that nothing changes a log unless the
owner edits it, and these two do. Either the rule has two named exceptions, or
they become Data Health findings like everything else. That is a decision to take
deliberately rather than leave implicit — and it is not 1.5.1 work.

Sizing: smaller than a migration. There is no backfill to write, no one-shot pass
to make idempotent across synced devices, and no history to get wrong.

### 8. Share an invoice/receipt straight to Expenses — S/M

Todoist p1. Filed for 1.5.1, cut on first pass, **restored** — the cut rested on
two claims about the code that are both false:

- *"It needs a share-extension target."* `BoatManagerShare/` already exists and
  ships. It never touches Core Data: it copies the file into the App Group inbox
  and foregrounds the app on `boatmanager://import`
  (`BoatManagerShare/ShareViewController.swift:1-12`). **There is no extension
  work in this at all.**
- *"It needs the normalised expense model first."* It does not. `Documents` already
  has a `log` relationship in the model, and an expense today **is** a `Log` —
  there is no `Expense` entity; `EditExpensesView` edits a selected `Log`
  (`Features/Core Features/Expenses/ExpenseLog/EditExpensesView.swift:17,27-33`)
  and the costs are columns on it.

All the work is at the receiving end, in the app:

- `DocumentDestination` (`Features/Core Features/Documents/InsertDocumentView.swift:22-54`)
  is a six-case enum — boat, newToDo, equipment, maintenanceTask, waypoint, crew.
  Add `.expense`, its label, its icon, `requiresPicker = true`, and a branch in the
  destination section plus its save path.
- **Pick the log, or start one.** The picker resolves a `Log` by date and port,
  and creates one for that date if none exists. 1.5.0 already set this precedent —
  a checklist run on a day with no log starts that log from yesterday's hours and
  position. Reuse it rather than inventing a second rule.
- Attach the file through the existing `Documents.log` relationship.

**The prompt sequence.** This is the whole feature, and it should be specified
rather than improvised. Four questions, each with a default good enough to accept:

1. **"What is this?"** — the destination row in the existing picker: Expense.
   Everything below is the Expense branch.
2. **"Which boat?"** — default boat, skipped if only one.
3. **"Which day?"** — date picker defaulting to today, showing the log it will
   attach to and its port. If no log exists for that date, the prompt says so
   plainly: *"No log for 14 Sep — start one?"* Starting it follows the 1.5.0
   rule: yesterday's hours and position.
4. **"What kind of cost?"** and the amount. The categories are the app's own,
   in the order `ExpensesSubView` already shows them: Mooring, Fuel, Pumpout,
   Water, Propane, Other.

**Route yard invoices to a maintenance task, not the log.** `Log.costMaintenance`
exists in the model but its field is commented out of the UI
(`ExpensesSubView.swift:129`) — maintenance money is summed from
`MaintenanceTasks` (labor / parts / yard). So the kind-of-cost prompt offers
**Maintenance** as a seventh choice that then picks a task, and files the document
against the task's own `Documents` relationship. This is precisely the failure the
expenses spec complains about — a $23,142 rebuild landing in free text — fixed for
the cost of one extra prompt.

**Never write `Log.cost`.** The generic column overlaps the category columns and
the expenses spec records that no consumer can tell which is authoritative. This
flow writes categories only.

**OCR is separable and out of scope here.** Ship the flow with the amount typed
by hand; a Vision text-recognition prefill is an independent follow-up that
changes no structure and can land in any release. The PDF filed against the right
log, with a cost on it, is the whole value — which is what the expenses spec says
about receipt capture anyway.

The one thing that does not survive: this cannot be documented as "file an expense"
in a way the normalised model would later contradict. It files a **document against
a log, with a cost**. That is exactly what the app means by an expense today.

### 12. Document why the app is shaped the way it is

Two design decisions explain most of what looks odd about the app, and neither is
written down anywhere a user can read:

1. **It started as a spreadsheet.** Many sheets, imported. That is why the schema
   is wide, why costs are columns rather than records, and why CSV import/export
   is a first-class path rather than an afterthought. An owner arriving with their
   own spreadsheet should be told this is the expected route in.
2. **The day log stands alone.** It is not a legal document but it is close, and
   nothing changes a log except the owner explicitly editing it. That is why a new
   log defaults to yesterday's rather than deriving itself, why auto-filled weather
   and tide are written once and read back verbatim, and why Data Health proposes
   rather than repairs. Equipment maintenance is the one deliberate exception —
   fully relational, because nothing else worked.

This is not marketing copy. It is the answer to "why does it do that", and it sets
the expectation that the app will not quietly change the owner's record. Both the
user guide (`docs/assets/boat-manager-user-guide.docx`) and a help.json entry
under *1. About* or *2. First Use*.

that this plan first cut is **in the release** — see item 8; the reasoning behind
the cut was wrong on the facts.

**Everything else on the Todoist list is 1.6 or later**, and none of it is a
